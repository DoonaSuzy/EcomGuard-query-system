## 6. ⑤ 可扩展性评估

### 6.1 加一个模块，现在要动 10 处

`aggregator.py` 共 266 非空行，其中**与具体模块绑定的有 34 行**（约 17 行/模块），散布在 10 个位置：

| 位置 | 行号 | 内容 |
|---|---|---|
| 目录常量 | 55–56 | `WIPO_DIR` / `CREDIT_DIR` |
| `sys.path` | 61 | `for _p in (str(WIPO_DIR), str(CREDIT_DIR))` |
| 环境默认值 | 68–69 | `WIPO_REPORTS_DIR` |
| 后端导入 | 72–75 | `build_api_router`、`register_exception_handlers`、`RequestContextMiddleware`、`wipo_lifespan` |
| glue 导入 | 79 | `credit_lifespan_enter/exit` |
| 产物路径 | 83–84 | `WIPO_DIST` / `CREDIT_DIST` |
| 单机产物兜底 | 94–95 | `_WIPO_DIST_STANDALONE` / `_CREDIT_DIST_STANDALONE` |
| 壳页卡片 | 200–206 | 两张 `a.card` + 标题 |
| lifespan 组合 | 236–241 | `wipo_lifespan` + `credit_lifespan_enter/exit` |
| 路由/重定向/挂载 | 272–296 | `include_router` ×2、`@app.get("/wipo")`/`("/credit")`、`_mount_module_frontend` ×2 |

**这就是「第三个模块要改 10 处、漏一处就 404/白屏」的根源。** 10 处里任何一处漏改都不会报错，只会静默失效（子路径不挂 → 404；lifespan 不组合 → `app.state` MISSING）。

### 6.2 注册表化后降到 1 处（原型已实测）

原型 `registry_proto.py`（**162 非空行**）用「两真模块 + 一假模块」验证：

- 通用机械 **127 行**（`ModuleSpec` + `create_app` + `SPAFiles` + 生命周期组合）
- `SPECS` 声明区 **31 行**（3 个模块，含注释）→ **每模块约 10 行声明**
- 假模块本体 20 行 + 1 个 `index.html`

实测 18/18 PASS：壳页自动生成 3 张卡片、`/wipo/` `/credit/` `/demo/` 全 200、`/demo` 307→`/demo/`、`/api/demo/ping` 返回 `{'module':'demo','state':'ready'}`（证明模块 lifespan 经 `AsyncExitStack` 被调用且共享 `app.state`）、原 16 条接口一条没丢、openapi 变 17 条。

**成本对比**：

| | 现状 | 注册表化 |
|---|---|---|
| 加第 3 个模块 | 改 `aggregator.py` **10 处 / ~17 行** | 加 1 条 `ModuleSpec`（~10 行） |
| 漏改后果 | 静默 404 / `app.state` MISSING | 不可能漏（单一数据源） |
| 通用代码量 | 266 行（含 34 行模块绑定） | 127 行通用 + 每模块 10 行 |

> 注册表化本身**不减少代码总量**，它消除的是「N 个模块 × 10 处手改」的乘法项。2 个模块时收益有限（省 7 行但多一层抽象）；**到第 3 个模块才真正回本**，第 4 个之后收益线性增长。

### 6.3 新增「不同逆向路径」场景的成本

credit 的抓取链路是**单体硬编码**：`credit_check.py`（417 非空行）里 `SEARCH_URL`(:58) / `DETAIL_URL`(:63) / `NORMAL`+`ALERT`(:68-69) / `STATUS_FIELDS`(:71) 是模块级常量，`CreditChecker.check_one()`(:256-330+) 一个方法里串起「goto 搜索页 → `#vcodeimg` 过码 → `selfObj.searchAjax` 重试 → 解析 list → 精确名匹配 → 抓详情 → 按 `STATUS_FIELDS` 取状态 → 判定」。

**加第二个数据源（另一个网站）的现状代价**：只能 fork 整个 `CreditChecker`，或把 `check_one` 拆成 `search(name)` / `detail(cand)` / `judge(fields)` 三段接口。

**建议**（不在本轮做，仅列入路线）：抽出 `SiteAdapter` 协议 ——

```
search(name) -> list[candidate]     # 站点差异只在这里
detail(candidate) -> dict[field]    # 字段名映射到统一键
judge(fields) -> verdict            # NORMAL/ALERT 口径可按站点覆盖
```

好处：新站点只需实现 3 个方法，`Worker`/`Store`/CSV/通知全复用；且 `NORMAL`/`ALERT` 词表可按站点覆盖（不同登记机关的用词不同）。代价：`check_one` 里 150+ 行与浏览器会话强耦合的逻辑要重新分层，属于**中等重构**，须有回归兜底（现有 189 项 + 201 项回归是安全网）。

### 6.4 新增「一个页面」的成本

| | WIPO | credit |
|---|---|---|
| 前端架构 | **无路由**，四 section 常驻靠 `.page.active` 显隐 | vue-router，6 条路由 |
| 加一页要改 | `App.vue` 加 section + `store.js` 加 page key + `components/Sidebar.vue` 加导航 + 页面标题映射（4 处） | 新增 1 个 view + `router/index.ts` 加 1 条 + `App.vue` 导航加 1 项（3 处） |
| 接口类型 | **手写** `web/src/api.js`（11 个 `export function`，`API_BASE='/api'`，无类型生成） | **代码生成** `openapi-typescript`（`npm run gen:api` → `types.d.ts` 15,632 B），`openapi-fetch` 编译期校验路径/参数/字段 |
| 加接口要改 | `api.js` 加函数 + 页面调用 | 后端加路由 → `gen:api` 重新生成 → 前端直接有类型 |

**这是两个模块最不一致的地方**：credit 有 openapi 驱动的类型链路（新接口零手写），WIPO 是手写 fetch 封装（新接口要手抄一遍路径与字段名）。**若统一，应把 credit 的做法推广到 WIPO**（后端已有 `/openapi.json`，只差 `gen:api` 脚本与前端改造），但 WIPO 前端无 TypeScript、无 openapi-fetch，属于**中等改造**，且会动 46 个 DOM 选择器契约所在的页面代码 → 须与 E2E 一起改。

### 6.5 容量与并发（已存在的硬约束）

- **credit 必须单进程单 worker**：`Worker._run()` 单线程串行消费内存队列，`_ensure_checker()` 懒建单个 Camoufox 实例。多进程部署会破坏串行语义且浏览器实例不共享。
- **WIPO 必须 `--workers 1`**：`check_runs` 是单行状态机，多进程下「哪个请求启动的检查」会错乱（README 已载明）。
- 结论：**当前架构的天花板是单机单进程**。要横向扩展必须先做「队列外置（Redis）+ 状态机多实例化」，这是路线图 P3 的内容，不是迁移缺陷。
