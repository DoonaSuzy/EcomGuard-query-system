# 架构演进路线（聚合系统）

> 2026-10-19 定稿。基准 commit `5d78487`，CI run 39191075156 四 job 全绿。
> 所有「现状」数字均可用附录 A 的命令复现；本文档只规划，不改代码。

## 0. 结论摘要

聚合系统当前处于「**结构已收敛、能力已验证、运维尚未产品化**」阶段：单入口双模块路由合并、
分库分表、统一错误外壳、CI 三 job 全部实测跑通。下一步演进的排序原则是
**先锁契约、再解耦合、后扩容量**——每期都以「上期产出的契约不变」为前提，避免边扩边改。

| 期 | 主题 | 核心动作 | 前置 |
|---|---|---|---|
| P1 | 契约固化 | 聚合层 pytest 契约测试（无需浏览器的 34 项） | 无 |
| P2 | 模块解耦 | `modules/` 改 submodule + 漂移检测 | P1（契约锁住合并层行为） |
| P3 | 容量与部署 | 队列外置 + 多实例 + 容器化 | P2（模块可独立演进） |
| P4 | 可观测与运营 | metrics / 审计 / 依赖健康巡检 | P3（有实例标识才有指标维度） |

## 2. P1 — 聚合层 pytest 契约测试（第 1 优先，工作量最小收益最大）

### 2.1 为什么是它

聚合层 328 行是全系统的**唯一接缝**，现在只被 37 项浏览器验收覆盖——而验收不适合
CI 快速反馈（起 uvicorn + Chromium 约 1 分钟）。README「待开发」第一条即此。

### 2.2 落地内容（预计 30~36 项断言，全部 TestClient 级）

1. **路由合并契约**：openapi paths = 16 条且无重复（比对 `aggregator.create_app().openapi()`）。
2. **lifespan 串联契约**：启动后 `app.state.store` / `app.state.worker` 存在；
   credit 与 WIPO 的 `app.state` 指向同一批对象（当前实现靠双赋值，正是 b158 的绕过点——
   契约先锁住现状，P2/credit 重构时此测试会逼出正确形态）。
3. **错误外壳契约**：credit 侧 404/422 响应体带 `success/error/request_id/code` 四键。
4. **壳页与重定向契约**：`/` 回壳页 HTML、`/wipo` 与 `/credit` 307、无 dist 时
   子路径不 500（SPAFiles 的 index 检查行为）。
5. **request_id 透传契约**：上游带 `X-Request-Id` → 响应原样返回。

### 2.3 验收标准

- `pytest tests_aggregated -q` 在**无浏览器、无 dist、无 MySQL** 的裸环境通过；
- CI tests job 增加第四套（与三套分开跑，沿用 conftest 隔离惯例）；
- accept 37 项保留为发布前门禁，不做替代。

## 3. P2 — modules/ 改 submodule + 漂移检测

### 3.1 问题

`modules/` 是两个上游仓库（WIPO_and_Brand、Business-License）的手工快照，
README 已列「漂移无自动检测」为已知风险。每次上游改动要 Copy-Item 同步，
历史上有一次覆盖过仓库内带修订头的文档（靠 `git checkout -- docs/` 恢复）。

### 3.2 落地内容

1. `git submodule add` 两个上游仓库到 `modules/wipo`、`modules/credit`；
2. CI 增加漂移检测 job：`git submodule status` 非最新时只警告不拦截（上游节奏与聚合仓不同步）；
3. **credit 侧前置重构**（P2 的实际工作量所在）：把 10 处模块级 `app.state` 引用
   改成 `request.app.state`（`api.py:579/587/593/595/602/608/621/642/655/661`）。
   改完跑 202 项回归——P1 的 lifespan 契约测试会同时验证合并层不受影响。
4. 漂移方向约定：**上游只进不退**（聚合仓跟随上游 tag，反向改动必须先提上游 PR）。

### 3.3 风险与规避

- submodule 指向 SSH remote（`ssh://git@ssh.github.com:443/...`），CI checkout 需
  token 化 URL 或改 HTTPS remote——落地时先在 CI 上验证 fetch，再合入。
- 改 `request.app.state` 的 10 处属行为等价重构，靠 202 + P1 契约双层回归兜底。

## 4. P3 — 容量与部署（解掉两个单进程绑定）

### 4.1 credit：队列外置

PNA 对比报告（docs/技术栈一致性评估与通用框架方案.md §5）已论证：PNA 的 Redis 外置队列
是聚合系统最值得移植的横切组件。落地形态：

1. `Worker.submit()` 抽象成接口：内存队列（现状，默认）+ Redis list（可选）；
2. credit 回归 202 项中 `_run()` 串行消费语义的测试**不改**——Redis 实现必须保持
   「单浏览器实例、作业串行」约束，只是把队列换载体；
3. 水平扩展单位是「每个 credit 实例 1 worker」，多实例共享 Redis 队列时
   `jobs`/`results` 表加 `instance_id` 列（分库方案不变）。

### 4.2 WIPO：check_runs 多实例化

单行状态机改为「活跃检查行」模型：`id` 不再固定 1，查询侧取 `started_at` 最新且
`status='running'` 的行。这是一次**带迁移的 schema 变更**——正好触发 WIPO 主文档里
预留的 Alembic 接入点（`app/main.py:15-18` 明文「留到第一次需要改列时再做」）。
实施顺序：接 Alembic → 生成首个迁移 → 改模型 → 44 契约 + 110 E2E 全量回归。

### 4.3 容器化

- credit 镜像必须 `python -m camoufox fetch`（README 已列风险）；
- 两模块镜像分开构建，聚合层只做编排（docker-compose：aggregator + mysql + 可选 redis）；
- `install_schedule_task.ps1` 的 Windows 计划任务路线与容器路线并存（各自部署形态不同）。

## 5. P4 — 可观测与运营

1. **结构化指标**：PNA 的 metrics 组件（计数器 + 直方图）按需移植；先埋
   「巡检作业成功/失败/耗时」「验证码通过率」「邮件发送成功率」三个核心指标；
2. **审计日志**：credit 作业级别已落库（jobs 表），补 WIPO 检查级别的事件行；
3. **依赖健康巡检**：credit 的 `healthcheck.py`（12 项自检 + 探针注入）已是最成熟实现，
   抽成两模块共享的 `common/healthcheck`，WIPO 侧复用同一套判定框架；
4. **上游依赖告警**：requirements 三模块并集目前手工维护，P2 之后由 submodule 的
   各自 requirements 派生（脚本生成 + `--check` 模式，PNA 的 schema 生成范式）。

## 6. 明确不做的（本路线边界）

- **不引入前端框架统一**：两套前端（无路由 Vue3 / 有路由 Vue3）各自成立，
  DOM id 零冲突已实测，合并产物层收益小于 110 项 E2E 的重写成本。
- **不引入 Alembic 之外的迁移工具**、**不引入 Prometheus/Grafana**（除非 P4 指标
  确有外部消费方）、**不动 WIPO 的无路由前端架构**（`.page.active` 是 E2E 契约主体）。
- **不改分库为分表**：分库已端到端跑通且边界更清晰，分表只作为同实例省资源的备选。
