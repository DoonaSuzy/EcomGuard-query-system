# 瑞数（Riverside / RS）逆向分析技术报告

> 适用对象：安全研究、自有系统防护评估、已获书面授权的渗透测试
> 编写日期：2026-10-18
> 报告口径：架构与分析方法论为主；**不含**可直接投用的令牌伪造器、指纹伪装配置、行为轨迹生成器（原因见 §3.4）
> 事实分级：`[公开]` 已公开研究可查证；`[实测]` 本项目在 creditchina.gov.cn 上实际观测；`[推断]` 基于结构合理推断，需自行验证

## 命名说明

瑞数信息的官方英文名为 **Riverside**，其动态防护产品线常被称作 **Botgate / 动态安全**，业内简写 **RS**。

题目中的 "Rebuild" 不是官方名称，也不是该产品的代号——很可能是对 RS 的误记。本报告统一用「瑞数 / RS」指代，避免沿用错误名称造成检索偏差。

## 0. 结论先行

| # | 判断 | 依据 |
| --- | --- | --- |
| 1 | 瑞数是**访问准入层**，不是业务数据加密层 | 它保护"你能不能发这个请求"，不加密业务字段。把"瑞数解密"理解成"解业务密文"是方向性错误 |
| 2 | 真正的技术门槛在**VM 解释器 + 环境契约**，不在混淆本身 | 混淆可自动化还原；VM 指令语义与环境读取面才是重活 |
| 3 | 单点绕过可做到，**长期稳定绕过不成立** | 挑战按版本/按会话重生成，指纹面持续加宽，维护成本是持续的 |
| 4 | 对"批量取数"这个业务目标，**授权通道的 TCO 低于自建绕过** | 见 §3.4 成本对比 |

一句话：**能做研究，能讲清原理，但不建议把"全自动绕过"当作生产方案**——不是技术上做不到，是它在成本、稳定性和法律三个维度同时不划算。

## 1. 架构解析

### 1.1 部署形态

瑞数以反向代理 / WAF 插件形式串在源站前面。客户端看到的仍是原站域名，但响应头会带特征：

| 信号 | 含义 | 本项目实测 |
| --- | --- | --- |
| `HTTP 412 Precondition Failed` | 挑战响应（非 403/503，是瑞数的标志性状态码） | `[实测]` 首次访问返回 412 |
| `x-via-jsl: <hash>, -` | 瑞数链路标记 | `[实测]` 见 `22e298e, -` |
| `ss: s` | 会话状态标记（部分部署出现） | `[实测]` 间歇出现 |
| Cookie 名随机（如 `6BVIhF5m7wQjO`） | 每部署随机生成，不可硬编码 | `[实测]` |
| `__jsl_clearance_s` / `__jsluid_s` / `insert_cookie` | 公开研究中反复出现的固定名 | `[公开]` |

### 1.2 五层机制总览

| 层 | 作用 | 可观测信号 | 分析入口 |
| --- | --- | --- | --- |
| L1 挑战下发 | 拦截首个请求，返回 JS | 412 + `text/html` 小页面 | 网络面板首跳 |
| L2 动态混淆 | 让静态分析不可复用 | 每次 JS 变量名/控制流/字符串编码都不同 | 两次抓包 diff |
| L3 VM 解释器 | 把真实逻辑藏进字节码 | 大整数数组 + `switch` 分发循环 + `while(1)` | 静态特征扫描 |
| L4 环境指纹 | 区分真实浏览器与自动化 | 大量 `navigator.*` / `canvas` / `WebGL` 读取 | 沙箱补环境时缺什么 |
| L5 令牌生成 | 产出可被服务端校验的 cookie | `Set-Cookie` / `document.cookie` 写入 | 值回溯 |

行为层（鼠标/滚动/节奏）在部分部署启用，本项目未观测到强行为校验。

### 1.3 412 握手时序

```
GET /target
  ← 412  +  <script> 混淆片段
GET /<随机路径>/<随机名>.js          ← 挑战主体
  ← 200  +  JS
[浏览器执行 JS：VM 运行 → 采集环境 → 计算令牌]
  → document.cookie = <随机名>=<令牌>
GET /target  (带 cookie)
  ← 200  +  正常内容
```

`[实测]` 本项目完整走过这条链：412 → `/z9ItHZeV1nhb/*.d07207d.js` → 200 + httpOnly cookie。**这条链是自动完成的**，浏览器不需要人工干预——这一点常被误解为"卡在 412"，其实 412 不是卡点。

### 1.4 动态混淆的实现方式

`[公开]` 常见手法，按还原难度递增：

| 手法 | 特征 | 还原难度 |
| --- | --- | --- |
| 标识符随机化 | `_0x1a2b` 类命名 | 低（作用域重命名） |
| 字符串数组 + 索引取值 | 顶部一个大数组，正文用 `arr[0x1f]` | 中（需要数组求值） |
| 字符串加密 | 数组元素本身是密文，取值时解密 | 中（需还原解密函数） |
| 控制流平坦化 | `switch` + 状态机，真实顺序被打散 | 高（需重建 CFG） |
| 不透明谓词 | 恒真/恒假条件包裹死代码 | 高 |
| VM 化 | 逻辑编译成自定义字节码 | 最高（见 §1.5） |

关键点：**同一份挑战 JS 只对应当前会话**。所以"把某个版本还原出来"没有长期价值，有价值的是**还原流水线**。

### 1.5 VM 解释器结构

`[公开]` 典型形态：

```js
var _bc = [12, 7, 93, 4, ...];        // 字节码数组
var _sp = 0;                           // 指令指针
while (1) {
    var _op = _bc[_sp++];              // 取操作码
    switch (_op) {
        case 12: /* ... */ break;
        case 7:  /* ... */ break;
        // 数十到数百个 case
    }
}
```

三层嵌套是常见形态：外层 VM 负责解密内层字节码，内层才是业务逻辑。识别要点：

| 特征 | 说明 |
| --- | --- |
| 单个超大函数（数千行） | 分发循环被内联展开 |
| 密集的整数比较 | `if (op === 0x1f) ... else if (op === 0x2a)` |
| 无意义的变量名 + 固定数组下标 | 寄存器/栈模拟 |
| `Function` / `eval` 构造 | 动态生成下一层 |

### 1.6 环境指纹采集面

`[公开]` 瑞数读取的环境面（按被检测强度排序）：

| 类别 | 具体项 | 自动化暴露风险 |
| --- | --- | --- |
| 原生函数完整性 | `Function.prototype.toString` 是否返回 `[native code]` | 极高（补环境最易露） |
| Navigator | `userAgent` / `platform` / `hardwareConcurrency` / `deviceMemory` / `languages` / `plugins` | 高 |
| 屏幕 | `screen.width/height` / `availWidth` / `colorDepth` / `devicePixelRatio` | 中 |
| Canvas | `toDataURL` 哈希（字体渲染差异） | 高 |
| WebGL | `getParameter(UNMASKED_VENDOR_WEBGL)` / 渲染器字符串 | 高 |
| Audio | `OfflineAudioContext` 输出哈希 | 中 |
| 时序 | `performance.now()` 精度、事件间隔分布 | 中 |
| 自动化痕迹 | `navigator.webdriver` / CDP 注入残留 / `window.chrome` 缺失 | 极高 |

**这一层是绕过成本的主要来源**——不是密码学，是"让假浏览器在所有维度上不可区分"。

### 1.7 令牌生成与轮换

`[推断]` 令牌的输入空间：

```
token = f(挑战种子, 环境指纹摘要, 时间戳, 服务端 nonce, 会话状态)
```

| 属性 | 表现 | 实测 |
| --- | --- | --- |
| 有效期 | 分钟级到小时级 | `[实测]` 本项目业务侧 vcode 窗口 5 分钟 |
| 轮换触发 | TTL 到期 / 会话变更 / 风控降级 | `[实测]` 过期后返回业务错误码要求重新验证 |
| 校验位置 | 服务端比对，客户端无法自证 | `[实测]` 手工写 cookie 骗过前端闸门，服务端仍拒 |
| 是否 httpOnly | 部分 cookie 为 httpOnly（JS 读不到） | `[实测]` 存在 httpOnly cookie |

**关键实测结论**：客户端 cookie 只驱动 UI 显隐，服务端独立校验。所以"改前端状态"没有任何绕过价值。

### 1.8 行为层

`[公开]` 部分部署采集：鼠标轨迹曲率、点击坐标分布、滚动速度、按键间隔、页面停留时长、请求节奏。判定方式多为统计检验（分布拟合 / 熵值 / 马尔可夫转移概率），而非硬规则。

本项目 `[实测]` 未触发行为校验——低频率 + 真实浏览器路径下，行为层不是瓶颈。

## 2. 分析方法论（八步）

> 前提：目标系统属自有资产，或已获书面授权。未授权分析在生产环境可能触犯 §5.1 所列法条。

### 2.1 基线捕获

**操作指引**

1. 用干净 profile 启动浏览器，清空 cookie/缓存。
2. DevTools → Network，勾选 `Preserve log`，禁用缓存。
3. 访问目标，记录完整首跳链：状态码、`Set-Cookie`、`x-via-jsl`。
4. 保存挑战 JS 原文（`Save all as HAR` + 单独存 JS）。
5. 等待 30 分钟以上，重复一次，用于 diff。

**常见坑点**

| 坑 | 后果 | 规避 |
| --- | --- | --- |
| 开着旧 cookie | 直接 200，看不到挑战 | 无痕窗口 + 清 cookie |
| `Preserve log` 未开 | 跳转后首跳记录丢失 | 必须开 |
| 只抓 XHR | 挑战是 document 级请求 | 过滤选 `All` |
| 复用同一 profile 多次 | 服务端记住会话，挑战不再下发 | 每次用新 profile |

**验证标准**：能稳定复现"412 → JS → cookie → 200"四段，且两次抓到的 JS 内容不同（证明动态性）。

### 2.2 静态分诊

**操作指引**

1. 文件大小、行数、是否单行压缩。
2. 搜关键词：`switch`、`while`、`0x`、`fromCharCode`、`atob`、`eval`、`Function(`。
3. 统计特征：
   - 大整数数组长度（> 1000 → VM 字节码嫌疑）
   - `case` 分支数（> 50 → 分发循环）
   - 字符串数组长度
4. 判定属于 §1.4 哪一档。

**常见坑点**

| 坑 | 后果 | 规避 |
| --- | --- | --- |
| 直接格式化后逐行读 | 数万行，读到崩溃 | 先做特征统计，再定位 |
| 忽略 `Function` 构造 | 漏掉动态生成的下一层 | 全局搜 `Function` / `eval` |
| 只看一层 | 嵌套 VM 只看到外壳 | 找"生成代码"的调用点 |

**验证标准**：能回答"几层 VM、字节码数组在哪、分发循环入口在哪、下一层如何生成"四个问题。

### 2.3 AST 还原

**操作指引**

1. 用 `@babel/parser` 解析，`sourceType: script`。
2. 按顺序跑变换：
   - 常量折叠（`evaluate`）
   - 字符串数组还原（先求值数组，再替换 `arr[i]`）
   - 作用域重命名（`scope.rename`）
   - 死代码消除（不透明谓词）
   - 控制流重建（`switch` 状态机 → 顺序语句）
3. 每步输出中间产物，diff 验证等价性。

工具链：`webcrack`（一体化）、`deobfuscator`（Babel 插件集）、自写 Babel 插件（可控性最好）。

**常见坑点**

| 坑 | 后果 | 规避 |
| --- | --- | --- |
| 一次性全跑 | 出错无法定位是哪步坏的 | 分步 + 每步存快照 |
| 字符串数组有副作用 | 求值顺序错导致值不对 | 用 AST 求值，不 `eval` |
| 改名冲突 | 不同作用域同名被合并 | 用作用域感知的 rename |
| 忽略 `with` / 动态作用域 | 还原后语义偏移 | 遇到就停，人工处理 |

**验证标准**：还原后代码在受控环境执行，产出与原版**逐字节一致**的令牌。不一致就是还原错了，不是"差不多"。

### 2.4 VM 指令流重建

这是整个分析里最有价值、也最费时的一步。

**操作指引**

1. 定位分发循环入口（`while(1)` 内的 `switch`）。
2. 在该函数入口下断点，或在源码中插入日志（`Function.prototype.toString` 检测可能因此报警，优先用断点而非改源码）。
3. 记录三元组序列：`(pc, opcode, operands)`。
4. 对每个 opcode，观察执行前后的状态变化（栈/寄存器/内存），归纳语义。
5. 建立 opcode → 语义 映射表。
6. 用映射表反编译字节码为可读伪代码。

**常见坑点**

| 坑 | 后果 | 规避 |
| --- | --- | --- |
| 断点打在错误层级 | 只看到外层解密循环 | 先确认是哪一层 |
| 单步执行 | 数十万条指令，不可行 | 条件断点 + 日志聚合 |
| 改源码插桩 | 触发 `toString` 完整性检测 | 用 DevTools 断点，不改文件 |
| 只记录 opcode 不记录操作数 | 语义无法确定 | 三元组一起记 |

**验证标准**：用映射表反编译后，能完整重放一次令牌计算，且结果与服务端接受的值一致。

### 2.5 环境契约提取

**操作指引**

1. 在 jsdom / 无头浏览器中执行挑战 JS。
2. 用 Proxy 包裹 `window`、`navigator`、`screen`、`document`、`performance`，记录所有读取路径。
3. 按"缺失 → 报错 → 补齐 → 再跑"循环，直到跑通。
4. 汇总读取路径清单 = **环境契约**。
5. 对每个读取项，标注：真实浏览器值 vs 自动化值 vs 是否参与令牌计算（用差分法：改一个值，看令牌是否变）。

**常见坑点**

| 坑 | 后果 | 规避 |
| --- | --- | --- |
| 只补"报错的" | 不报错但参与计算的项被漏掉 | 用差分法逐个试 |
| 补齐但值不对 | 跑通但令牌不被接受 | 契约 = 路径 + 值域，两者都要 |
| `toString` 未处理 | 补的函数被识别为伪造 | 必须返回 `[native code]` |
| 忽略读取顺序 | 部分逻辑依赖调用时序 | 记录顺序 |

**验证标准**：契约清单覆盖所有被读取路径，且用该契约构造的环境能产出**服务端接受**的令牌。

### 2.6 令牌公式回溯

**操作指引**

1. 在 `document.cookie` setter 上下断点，抓到最终值。
2. 沿调用栈向上，定位计算函数。
3. 对每个输入做差分：固定其余、改一个，看输出变化。
4. 判定每个输入的角色：直接参与 / 摘要后参与 / 仅作盐 / 不参与。
5. 归纳公式结构（哈希？拼接？加密？）。

**常见坑点**

| 坑 | 后果 | 规避 |
| --- | --- | --- |
| 只看最终值 | 中间步骤被优化掉 | 在多个层级同时下断点 |
| 输入含服务端 nonce | 离线重放必然失败 | 先确认是否依赖 nonce |
| 忽略时间戳精度 | 差几毫秒就失效 | 记录原始精度 |
| 忽略编码 | hex/base64/URL 编码混淆 | 逐层解码确认 |

**验证标准**：给定相同输入集，重算结果与抓包值**完全一致**；且服务端接受该值。

### 2.7 加密算法定位与密钥提取

这一节回答「瑞数到底加没加密、密钥在哪」。先说结论，再说方法。

**结论**：瑞数的主链路**通常不做经典密码学意义上的"业务数据加密"**，而是：

| 层 | 实际形态 | 是否有"可提取的密钥" |
| --- | --- | --- |
| 挑战 JS 自身 | 字符串用自定义编码 + VM 运算还原 | 无固定密钥；密钥材料由 VM 运行时合成 |
| 令牌计算 | 自定义哈希/混合运算（非标准 AES/RSA/SHA 的直接调用） | 无；输入是环境指纹 + nonce 的摘要 |
| 业务参数 | 部分部署把参数整体包成一个不透明 blob（如 `rcwCQitg=<长串>`） | 有，但密钥在 VM 内动态生成，且按会话变化 |
| 通信层 | 标准 TLS | 有（证书），但不是分析目标 |

`[实测]` 本项目观察到的正是第三种：明文业务参数被整体替换为一个约 700–1500 字符的点分段 blob，作为单个 query 参数发出。这不是"把字段逐个加密"，而是"把整个请求语义打包"。

**定位标准加密原语的四种方法**

| 方法 | 操作 | 适用 |
| --- | --- | --- |
| 常量指纹 | 搜 AES S-box 首字节序列 `63 7c 77 7b f2 6b 6f c5`；搜 MD5 初始向量 `67452301 efcdab89`；搜 SHA-256 初始常量 `6a09e667 bb67ae85` | 标准算法被直接内联时 |
| 库调用检测 | 搜 `CryptoJS`、`createCipheriv`、`subtle.encrypt`、`asmCrypto`、`sjcl` | 用了现成库时 |
| 结构特征 | AES 有 10/12/14 轮循环 + 列混合；RSA 有大整数模幂；哈希有固定压缩函数 | 手写实现时 |
| 行为探测 | 改输入长度 1 字节，看输出长度变化：分组密码输出按块跳变，流密码/哈希长度不变 | 快速判定类别 |

**常见坑点**

| 坑 | 后果 | 规避 |
| --- | --- | --- |
| 把 base64 当加密 | 白忙一场 | 先试解码：长度是 4 的倍数、字符集 `A-Za-z0-9+/=` |
| 把自定义编码当加密 | 找不到密钥 | 看是否有固定映射表（替换密码特征） |
| 只找标准算法 | 漏掉自定义混合运算 | 优先做差分分析，而非算法匹配 |
| 假设密钥是硬编码字符串 | 在 VM 场景必然失败 | 密钥多为运行时派生 |
| 忽略 IV/nonce 随请求变化 | 重放必然失败 | 对比两次请求的相同段/不同段 |

**密钥提取的四条路径（按可行性排序）**

1. **运行时拦截**（最可靠）：在加密函数入口/出口下断点，直接读参数和返回值。密钥若是派生值，在派生完成的瞬间抓。
2. **内存 dump**：加密执行后 dump 堆，搜高熵字节串（熵 > 7.5 bit/byte、长度 16/24/32 的倍数）。
3. **静态回溯**：从密文产出点反向做数据流分析，追到常量或环境读取。
4. **已知明文攻击**：若已知明文-密文对，可反推密钥流（流密码）或验证分组模式（分组密码）。

`[实测]` 本项目未做密钥提取——因为已交付方案走真实浏览器路径，不需要离线重算令牌。这是有意的取舍，不是能力缺失。

**对称 / 非对称的判定**

| 判据 | 对称 | 非对称 |
| --- | --- | --- |
| 密文长度 | 与明文线性相关（按块） | 固定（等于模长） |
| 输出长度 | 可预测 | 与输入无关 |
| 计算耗时 | 微秒级 | 毫秒级（大数运算） |
| 代码特征 | 轮函数循环 | 模幂 / 蒙哥马利乘法 |

反爬场景里**非对称极少用于业务数据**（太慢），常见于许可证/授权校验。令牌计算用哈希或对称更合理。

**密文逆向解密的标准流程**

```
1. 定位密文产出点（请求发出前最后一个赋值）
2. 向上追 1 层，确认是"加密"还是"编码"还是"打包"
3. 若是打包：拆结构（分隔符 / 长度前缀 / TLV）
4. 若是编码：逐层解码（URL → base64 → hex）
5. 若是加密：判定对称/非对称 → 定位密钥来源 → 复现
6. 用同一输入重算，与抓包逐字节比对
7. 冷启动复验（新会话）
```

**验证标准**：给定同一组输入（含 nonce/时间戳），重算密文与抓包值**完全一致**；且服务端接受该密文。只做到"能解出明文"不算完成——那只能证明你理解了算法，不能证明你能生成合法请求。

> 提醒：上述方法用于理解自有/授权系统的数据流。对第三方系统提取密钥并伪造请求，属 §5.1 所列风险区。

### 2.8 验证标准汇总

| 层级 | 通过标准 | 不通过的表现 |
| --- | --- | --- |
| 基线 | 四段链可复现，两次 JS 不同 | 直接 200（说明有旧会话） |
| 分诊 | 四问可答 | 说不清几层 |
| AST 还原 | 令牌逐字节一致 | "大致一样" |
| VM 重建 | 可完整重放 | 只能跑一半 |
| 环境契约 | 契约环境产出被接受 | 跑通但 412/403 |
| 令牌公式 | 重算 == 抓包 | 差一位 |
| 端到端 | 新会话冷启动成功 | 只在热会话里成功 |
| 密钥/密文 | 同输入重算密文逐字节一致且服务端接受 | 只能解出明文 |

## 3. 分层方案的工程现实

### 3.1 为什么"离线生成令牌"通常不成立

三个结构性障碍：

1. **服务端 nonce**：部分部署把一次性 nonce 嵌在挑战里，令牌与该 nonce 绑定，重放窗口极短。
2. **时间耦合**：令牌含时间戳，且服务端校验时钟偏移。
3. **会话耦合**：令牌与首次握手的会话标识绑定，换会话即失效。

`[实测]` 本项目验证过：手工写 cookie 能骗过前端显隐逻辑，服务端仍返回业务错误码。**客户端状态可伪造，服务端校验不可伪造**。

### 3.2 指纹伪装的检测对抗

指纹伪装不是"改几个字段"，是"在所有维度上自洽"。检测方常用交叉验证：

| 交叉检查 | 矛盾示例 |
| --- | --- |
| UA 声明 vs 实际能力 | UA 说 Chrome 120，但缺 `chrome.runtime` |
| 屏幕 vs 视口 | `screen 1920×1080` 但视口 800×600 且 `devicePixelRatio=1` |
| Canvas vs 字体 | Canvas 哈希对应 Linux 字体集，但 UA 说 Windows |
| WebGL vs 驱动 | 渲染器字符串与平台不匹配 |
| 时序 vs 硬件 | `hardwareConcurrency=2` 但计算吞吐像 16 核 |

任何一处不自洽都可能被单独标记。**这是持续维护工作，不是一次性配置**。

### 3.3 行为模拟的统计检验

行为层的判定多基于分布而非阈值：

| 检验维度 | 自动化特征 |
| --- | --- |
| 鼠标轨迹 | 直线化、曲率恒定、速度方差过小 |
| 点击落点 | 集中在元素中心，缺少偏移 |
| 滚动 | 匀速、无回滚、无惯性 |
| 按键间隔 | 方差过小（人类有显著抖动） |
| 请求节奏 | 间隔过于规整 |

要让模拟通过统计检验，需要生成**带真实噪声的分布**——这本质上是"做一个足够好的假人"，投入产出比很差。

### 3.4 成本对比：绕过 vs 授权通道

| 方案 | 一次性投入 | 持续成本 | 稳定性 | 法律风险 |
| --- | --- | --- | --- | --- |
| 自建全自动绕过 | 高（VM 重建 + 契约 + 伪装） | 高（版本更新即失效，需持续跟进） | 低 | 高 |
| 半自动（人工过码 + 会话复用） | 低 | 低（人工介入） | 中 | 中 |
| 官方 API / 数据授权 | 低 | 按量付费 | 高 | 无 |
| 商业数据服务商 | 低 | 按量付费 | 高 | 无 |

> 上表为定性判断，不含具体报价。实际选型应按"年化总成本 = 一次性投入/摊销年限 + 年维护人力 × 人力成本 + 失效导致的业务中断损失"计算。

**本报告不提供**：可直接投用的令牌伪造器、针对瑞数检测面的指纹伪装配置、行为轨迹生成器。原因不是技术不可行，而是这三项的组合等于一套通用绕过工具，其主流用途是未授权批量访问；同时它们在任何一次版本更新后即失效，对读者没有长期价值。**分析方法论**（§2）才是可迁移的资产。

## 4. 调试技巧（分析向）

### 4.1 DevTools 断点策略

| 场景 | 手法 | 注意 |
| --- | --- | --- |
| 找不到入口 | `Event Listener Breakpoints` → `Script` → 全勾 | 噪音大，配合 `Call Stack` 过滤 |
| 定位 cookie 写入 | 在 `document.cookie` 的 setter 上下断点（Sources → 右键 → `Add conditional breakpoint`，或用 `Object.defineProperty` 在页面上下文重定义） | httpOnly cookie 抓不到，需看响应头 |
| 定位请求 | XHR/fetch breakpoint，URL 填特征串 | 挑战请求是 document 级，XHR 断点抓不到 |
| 条件断点 | 在分发循环入口设 `pc > N` | 跳过预热阶段 |
| 黑盒化 | `Sources` → `Blackbox script` 跳过第三方库 | 避免单步掉进库函数 |

### 4.2 反调试识别与处置

| 反调试手法 | 识别信号 | 分析期处置 |
| --- | --- | --- |
| `debugger` 死循环 | 断点后反复停在同处 | DevTools 右键 `Never pause here`；或在 `debugger` 语句所在行禁用断点 |
| 时间差检测 | 单步后代码走异常分支 | 用 `Emulation` 或改写 `performance.now`（仅分析环境） |
| `console` 检测 | 打开 DevTools 即跳转/清空 | 用独立调试实例，不共享控制台 |
| 函数 `toString` 校验 | 补环境后立即失败 | 补的函数必须返回 `[native code]` |
| 栈深度/调用者检测 | 断点后行为改变 | 用 `debugger` 语句而非断点，减少栈扰动 |

原则：**在隔离环境里做，不在生产页面上做**。生产页面上的一切改动都可能被服务端记录。

### 4.3 内存与字符串提取

| 目标 | 手法 |
| --- | --- |
| 已解密的字符串 | 在字符串数组还原函数返回处下断点，dump 返回值 |
| 字节码 | 在 VM 初始化后 dump 字节码数组 |
| 运行时对象 | DevTools `Memory` → `Heap snapshot`，按构造函数名过滤 |
| 网络层明文 | 在 `XMLHttpRequest.prototype.send` / `fetch` 入口 hook，记录参数（仅分析环境） |

### 4.4 符号与结构还原

1. 从调用图反推模块边界（高频互相调用的函数聚类）。
2. 按"输入类型 → 输出类型"给函数命名（`_0x1a2b(a,b) → string` → `computeToken`）。
3. 建立数据流图，标注每个值的来源（环境 / 常量 / 服务端）。
4. 用类型推断（`ts-morph` / JSDoc 注解）固化理解。

### 4.5 常见坑点清单

| # | 坑 | 规避 |
| --- | --- | --- |
| 1 | 把 412 当卡点 | 412 是握手第一步，浏览器会自动完成 |
| 2 | 只抓 XHR | 挑战是 document 请求 |
| 3 | 复用会话导致看不到挑战 | 每次新 profile |
| 4 | 改源码插桩触发完整性检测 | 用断点 |
| 5 | 还原后"大致一样"就收工 | 必须逐字节一致 |
| 6 | 补齐环境但值域不对 | 契约 = 路径 + 值域 |
| 7 | 在热会话里验证成功就以为通了 | 必须冷启动验证 |
| 8 | 忽略 httpOnly cookie | 看响应头 `Set-Cookie` |
| 9 | 把业务错误码当网络错误 | 区分 HTTP 状态与业务 `code` |
| 10 | 用固定间隔请求 | 触发节奏检测 |

## 5. 合规边界

### 5.1 法律框架（中国大陆）

| 法规 | 相关条款 | 与逆向分析的关系 |
| --- | --- | --- |
| 《网络安全法》 | 第 27 条：不得从事非法侵入、干扰正常功能、窃取数据 | 未授权绕过技术措施可能落入 |
| 《数据安全法》 | 数据分类分级、重要数据出境 | 批量获取公开数据也需评估 |
| 《个人信息保护法》 | 处理个人信息需合法性基础 | 企业信息中若含个人信息（法定代表人等）需注意 |
| 《反不正当竞争法》 | 第 12 条：妨碍、破坏其他经营者合法提供的网络产品运行 | 商业性批量抓取的主要风险条款 |
| 《刑法》 | 第 285 条（非法获取计算机信息系统数据）、第 286 条（破坏计算机信息系统） | 情节严重的刑事风险 |

**关键区分**：

| 情形 | 风险等级 |
| --- | --- |
| 分析自有系统 / 已获书面授权的目标 | 低（仍需遵守授权范围） |
| 研究公开样本、离线分析（不接触生产） | 低 |
| 低频、遵守 robots、仅取公开信息、不绕过技术措施 | 中低 |
| 绕过技术措施批量获取 | 中高 |
| 绕过 + 高频 + 数据转售 | 高 |

### 5.2 授权测试的红线

即使有授权，以下行为通常超出授权范围：

1. 对非授权域名发起请求（含第三方 CDN、统计、认证服务）。
2. 使用真实用户凭据。
3. 造成服务可用性下降（压测式并发）。
4. 留存、外传业务数据。
5. 将绕过方法用于授权范围外的其他站点。

### 5.3 本项目（creditchina.gov.cn）的具体判断

| 维度 | 事实 | 判断 |
| --- | --- | --- |
| 数据性质 | 企业工商登记信息，依法公开 | 公开数据，抓取本身不当然违法 |
| 是否绕过技术措施 | 已交付方案**不绕过**瑞数，走真实浏览器正常路径 | 低风险 |
| 频率 | 3.5–6.5 s/家，单批 ≤ 50 | 低频，非压测 |
| 用途 | 内部风控核验，不转售 | 合规 |
| 验证码 | 自动识别用于自身低频访问 | 需在内部制度中明确用途边界 |
| 建议 | 上线前与法务确认内部使用范围；保留查询日志 | — |

**明确不做**：不构造离线令牌生成器、不做指纹伪装以欺骗风控、不做行为模拟以规避检测。已交付工具的全部请求都由真实浏览器发起，与人工操作在协议层不可区分。

## 6. 落地建议

### 6.1 官方与授权数据通道（推荐）

| 通道 | 适用 | 说明 |
| --- | --- | --- |
| 国家企业信用信息公示系统（gsxt.gov.cn） | 单点核验 | 官方，可出《企业信用信息公示报告》 |
| 信用中国数据开放 / 共享平台 | 机构批量 | 面向机构的授权数据服务 |
| 商业数据服务商（企查查/天眼查/爱企查等） | 批量 + API | 有正式 API 与 SLA，含状态变更推送 |
| 风险数据服务商（百融/冰鉴等） | 风控场景 | 提供企业风险评分与异动监控 |

对"批量 + 异常提醒"这个需求，**商业数据服务商的 API + webhook 推送**是最省事的：它们本身就在做状态变更监控，比自己轮询更及时。

### 6.2 已交付工具的正确定位

| 场景 | 是否适用 |
| --- | --- |
| 中小批量（≤ 50 家）定期巡检 | 适用 |
| 一次性核对名单 | 适用 |
| 需要实时状态变更推送 | 不适用（轮询有延迟） |
| 数百家以上 | 不适用（建议转 API） |
| 需要历史状态轨迹 | 不适用（只能取当前状态） |

### 6.3 规模化路径

```
≤ 50 家/批  →  credit_check.py（已交付）
50–500 家   →  商业 API（按量）
> 500 家    →  商业 API + 增量同步 + webhook
需要历史    →  商业 API（含变更记录）
```
