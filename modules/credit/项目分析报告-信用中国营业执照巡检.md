# 信用中国营业执照巡检 · 项目分析报告

> 项目周期：2026-10-17 ～ 2026-10-18
> 目标站点：www.creditchina.gov.cn（信用中国）
> 业务目标：销售部门批量核验一批公司主体的工商登记状态，异常自动提醒主管
> 报告性质：**本项目实际做了什么、用了什么方法、哪些路走通了、哪些是死路**
> 与《瑞数逆向分析技术报告》的区别：那份讲通用原理，这份讲本项目的具体执行

---

## 1. 项目定位与约束

### 1.1 起点

| 项 | 内容 |
| --- | --- |
| 原始需求 | 批量检查一批公司营业执照状态，异常自动提醒主管 |
| 隐含约束 | 不触发风控、频率尽量低、合法合规 |
| 起点认知 | 只知道"信用中国有瑞数（RS）防护"，其余未知 |

### 1.2 三条硬约束及其对方案的影响

| 约束 | 对技术选型的实际影响 |
| --- | --- |
| 不触发风控 | 否决了"直连接口 + 伪造签名"路线，只能走真实浏览器 |
| 频率尽量低 | 定下 3.5–6.5 s/家随机间隔，单批 ≤ 50 家 |
| 合法合规 | 否决了指纹伪装、行为模拟；只走页面正常浏览路径 |

**这三条约束直接决定了最终架构**：Camoufox（真实浏览器内核 + 指纹伪装）+ 自动过码 + 页面内 JS 调用，而不是裸 HTTP 客户端。后文所有技术选择都能回溯到这三条。

## 2. 分析方法与执行顺序

整个项目按"先证伪假设，再定方案"推进。下表是实际执行顺序，含每步用的工具与产出。

| 阶段 | 方法 | 工具 | 产出 / 结论 |
| --- | --- | --- | --- |
| P1 入口侦察 | 点击首页搜索按钮 + 全量抓包 | camoufox `inject_hook_preset(xhr/fetch)` + `list_network_requests` | **零请求** → 发现按钮是 `window.open` 不是 XHR |
| P2 源码取证 | 拉取并落盘页面 JS，逐行读 | `scripts(action=get)` → 本地 `scripts/` 目录 | 5 个文件共 45.8 KB，定位全部接口契约 |
| P3 接口契约 | 从源码提取 URL、参数、成功码 | 静态读码 | `catalogSearchHome` 全明文，无加密参数 |
| P4 卡点判定 | 对比 412 与业务 400 的差异 | `list_network_requests` 状态码聚合 | **412 不是卡点**（`info` 接口同批 200） |
| P5 闸门定位 | 读 `vcodeswitch` + 验证码逻辑 | 静态读码 `vcode.js:1` | 强制验证码，`vcodeswitch=1` 恒定 |
| P6 服务端校验实证 | 手工写 cookie 后重放请求 | `evaluate_js` 改 cookie + `fetch` | 客户端放行、**服务端仍 400** → 判定为会话级校验 |
| P7 验证码可行性 | 取图 + OCR 基准测试 | `ddddocr` + 自写 `bench_captcha.py` | 45% → 52.6%（3× 放大） |
| P8 字段定位 | 详情页响应结构解析 | `get_network_request(include_body)` | `headEntity.status` 是真实字段 |
| P9 语义校准 | 用已知状态企业做反证 | 批量跑已知吊销/注销企业 | `total=0` = 未收录 ≠ 一定注销，但索引只收在册主体 |
| P10 假阳性修复 | 构造名称不完整反例 | 跑京东/字节两条 | 模糊匹配会误取别家状态 → 改为精确匹配 |
| P11 工程化 | 封装 CLI + 提醒 + 文档 | Python | `credit_check.py` / `notify.py` / README |
| P12 端到端验证 | 自测 + 批量 + 推送打桩 | 实跑 | 吞吐 11 s/家，推送链路 `errcode=0` |

## 3. 关键技术发现（附证据）

### 3.1 死路一：点搜索按钮抓不到包

**做法**：按常规思路，在首页点搜索按钮，hook fetch/XHR 看请求。

**结果**：全空。连续多轮排查，怀疑被拦截。

**真相**（`scripts/temp.js:120-154`）：

```js
$(".search_btn").bind('click', function () {
  var url = config.FEIP + 'xinyongxinxi/index.html' + '?...&keyword=' + encodeURI(...);
  window.open(url);          // 只拼 URL 跳转，不发任何数据请求
});
```

**对照**：同一文件 `:144` 是拼 URL 的那行，`:145` 是 `window.open(url)`；站内文章分支在 `:147-150`。真正发请求的 `searchAjax` 在 `companysearch.js:115`，由结果页加载时自动触发（`companysearch.js:176` 的 `selfObj.paginationEvent(1)`）。

**教训**：抓不到包不等于被拦截。**先确认这个交互到底发不发请求**，再谈绕过。

**代价**：这一轮排查占用了相当篇幅，是项目里最大的一次方向性误判。

### 3.2 接口契约：全明文，无加密

`scripts/config.js:11-15` 定义三个域名常量：

```js
window.config = {
  IP:      'https://public.creditchina.gov.cn/private-api/',
  FEIP:    'https://www.creditchina.gov.cn/',
  VcodeIP: 'https://public.creditchina.gov.cn/private-api/'
};
```

`scripts/companysearch.js:115-170` 的搜索请求：

```
GET https://public.creditchina.gov.cn/private-api/catalogSearchHome
  ?keyword=...&scenes=defaultScenario&tableName=credit_xyzx_tyshxydm
  &searchState=2&entityType=1,2,4,5,6,7,8&templateId=&page=1&pageSize=10
```

**结论**：业务参数全部明文，**没有业务层加密**。这否定了"需要还原加密算法"这个初始假设——本项目根本不需要做密钥提取。

> 这也是我后来在通用报告里写"瑞数主链路通常不做经典业务加密"的实证来源。

### 3.3 卡点判定：412 是假象，验证码才是真闸门

**证据链**：

| 观测 | 结果 | 推论 |
| --- | --- | --- |
| 首次访问 | 412 → `/z9ItHZeV1nhb/*.d07207d.js` → 200 | RS 两跳被 Camoufox 自动通过 |
| 同批 `GET /private-api/info` | 200 | RS 签名有效，412 不是障碍 |
| 带 keyword 进结果页 | `catalogSearchHome` → 400 | 业务层拒绝 |
| 响应体 | `{"status":10001,"message":"验证码已失效，请重新申请验证码！"}` | 验证码会话缺失 |

**判定**：卡点在验证码，不在瑞数。这个判定把后续工作量从"VM 逆向"降到"验证码识别"，是整个项目最重要的一次收敛。

### 3.4 服务端校验实证：客户端 cookie 可伪造，服务端不行

**做法**：在页面内执行 `document.cookie = "vcode=1;path=/"`，然后重新触发搜索。

**结果**：

| 层 | 行为 |
| --- | --- |
| 客户端 | `getCookie('vcode') == ''` 判断通过，直接调 `searchAjax()` |
| 服务端 | 仍返回 400 + `status:10001` |

**结论**：`vcode` cookie 只是 UI 状态同步，服务端另有一份会话级验证码状态。**所有"改前端状态"类绕过思路在此项目上无效**。

这条实证也直接支撑了后来"不做离线令牌生成器"的决策。

### 3.5 验证码：规格、识别率、通过策略

**规格实测**：

| 项 | 值 |
| --- | --- |
| 接口 | `GET /private-api/verify/getVerify?_v=<random>` |
| 类型 | `image/jpeg` |
| 尺寸 | 95 × 25 px |
| 大小 | 1.7–2.6 KB |
| 内容 | 4 位数字 + 字母（大小写混合） |
| 校验 | `POST /private-api/verify/checkVerify`，`verifyInput=<4位>` |

**识别率基准**（`bench_captcha.py` / `bench_ocr_variants.py` 实跑）：

| 方案 | 样本 | 成功率 | 平均过码次数 |
| --- | --- | --- | --- |
| ddddocr 原图 | 20 张 | 45.0%（9/20） | ~2.2 |
| ddddocr 3× LANCZOS 放大 + 灰度 | 19 张 | **52.6%**（10/19） | ~1.9 |

**工程决策**：单次五成不够，但**换图重试**把"过码"变成确定事件。代码里 `MAX_CAPTCHA_TRY = 12`，实测首次查询 1–5 次内必过。

**关键收益**：`vcode` 有效期是 **5 分钟**（`vcode.js:97-102` 里 `5 * 60 * 1000`，函数名 `setCookieExpireInOneMinute` 是误导）。过一次码后 5 分钟内可连续查数十家——这是方案能低成本跑量的根本原因。

### 3.6 字段定位：`headEntity.status`

详情页响应结构：

```
{ data: {
    headEntity: { jgmc, tyshxydm, status, record_source },   ← status 在这里
    data: { table_name, dataSource, entity: {...} }           ← 另一份可能含 org_statu
} }
```

**工程处理**：`STATUS_FIELDS` 定义为 7 个候选字段的元组，按序回退：

```python
STATUS_FIELDS = ("status", "org_statu", "reg_status", "registration_status",
                 "business_status", "operating_status", "ent_status")
```

理由：不同 `tableName` 返回的字段名不一致，硬编码单一字段会在换表时静默失败。

**同类问题**：`accurate_entity_code` 可能为 null，已回退取 `headEntity.tyshxydm`。

### 3.7 语义校准：`total=0` 到底意味着什么

这是本项目最容易被做错的一处。用已知状态企业做反证：

| 企业 | 实际状态 | 信用中国搜索结果 |
| --- | --- | --- |
| 石家庄三鹿集团 | 已吊销注销 | `total=0` |
| 深圳市快播科技 | 已注销 | `total=0` |
| 钰诚国际控股集团 | 已吊销 | `total=0` |
| 阿里巴巴(中国) | 存续 | `total=21` |
| 上海冠生园食品 | 存续 | `total=5` |

其详情表名为 `credit_scjdglzj_fr_gscxqy` —— **工商存续企业**。即该索引只收在册主体。

**结论**：`total=0` 强烈提示主体已退出经营，但**不能等同于"一定注销"**——新设企业、名称变更、库同步延迟也会查不到。所以判定为 `notfound` 并**提醒主管 + 人工核验**，而不是直接判"已注销"。

**反向注意**：`昆明泛亚有色金属交易所` 虽被处罚但**仍是存续**，返回「存续」是正确结果。行政处罚 ≠ 主体注销，两者不能混。

### 3.8 假阳性修复：模糊匹配是陷阱

**问题**：早期实现取搜索结果第一条兜底。实测反例：

| 输入 | 兜底取到 | 该主体状态 | 后果 |
| --- | --- | --- | --- |
| 京东世纪贸易有限公司 | 上海京东世纪贸易有限公司 | 存续 | 误报为"正常" |
| 字节跳动有限公司 | 跳动字节科技(北京)有限公司 | 存续 | 误报为"正常" |

**为什么危险**：把别家公司的「存续」当成输入公司的状态，会让销售以为这家客户没问题，实际名称都没对上。**假阳性比查不到更危险**。

**修复**（`credit_check.py:281-293`）：删除兜底，改为全称精确相等（全角括号归一 + 去空白）才认；不匹配则返回 `unknown` 并列前 3 个候选全称。

```python
target = next((r for r in lst
               if norm_name(r.get("accurate_entity_name")) == norm_name(name)), None)
if target is None:
    out["判定"] = "unknown"
    out["备注"] = f"无精确同名主体，未判定状态。候选：{cands}（请核对全称后重查）"
```

### 3.9 又一个假象：页面"没有找到数据"不等于接口返回 0 条

`companysearch.js:115-170` 的 success 分支（`total<=0`）和 error 分支**走同一套 DOM**：隐藏结果区、显示 `.no-data`。

所以页面上看到"很抱歉，没有找到您搜索的数据"时，可能是：
1. 真的 0 条
2. 请求 400
3. 网络错误

**工程处理**：不读页面文案，只读响应 JSON 的 `status` 与 `data.total`。

### 3.10 其他死路（保留以免重复）

| 死路 | 现象 | 原因 | 最终方案 |
| --- | --- | --- | --- |
| `fetch` + `blob()` 取验证码图 | 间歇性 `NetworkError` | OpaqueResponseBlocking | 直接给 `img.src`，等 `complete && naturalWidth>0` |
| `fetch` + `arrayBuffer()` | `Accessing TypedArray data over Xrays is slow` | Firefox Xray 限制 | 同上 |
| `canvas.drawImage` + `toDataURL` | `The operation is insecure` | 跨域污染 | 用 Playwright 元素截图 |
| 首页点搜索按钮 | 抓不到任何请求 | `window.open` 跳转 | 直接构造带 keyword 的 URL 导航 |
| 手工写 `vcode` cookie | 客户端放行、服务端 400 | 服务端会话校验 | 真实过码 |
| GLM-4.6V-Flash 识别汉字 | HTTP 429 | 免费额度并发限制 | 用户纠正为数字字母后走 ddddocr |
| 在 `evaluate_js` 里读 `window.selfObj` | `undefined` | 页面脚本变量不在可访问全局 | 用 `search_code` 在已加载脚本里搜 |

> 最后一条值得单独强调：**变量不可见 ≠ 脚本没跑**。当时差点据此推翻源码结论，实际是作用域问题。

## 4. 最终架构与关键参数

### 4.1 架构

```
credit_check.py
├─ Camoufox 启动（指纹伪装，非裸 requests）
├─ 导航到带 keyword 的搜索页（页面自动触发 catalogSearchHome）
├─ 拦截响应 → 判断 status
│   ├─ 1/200  → 取 data.list
│   └─ 10001  → 过码后重试
├─ 精确名称匹配 → 拿 uuid + entityType
├─ 导航详情页 → 拦截 getTyshxydmDetailsContent
├─ 从 headEntity 取 status → 判定
└─ 写 CSV
        ↓
notify.py → webhook / SMTP / 打印
```

### 4.2 关键参数表

| 参数 | 值 | 依据 |
| --- | --- | --- |
| `SEARCH_OK` | `{1, 200}` | 实测成功码是 `status=1`，不是 HTTP 200 |
| `VCODE_EXPIRED` | `{10001}` | 实测"验证码已失效"业务码 |
| `MAX_CAPTCHA_TRY` | 12 | 单次 52.6% → 12 次失败概率 < 0.02% |
| `CAPTCHA_TTL` | `5 * 60` | 源码 `5*60*1000`，非函数名暗示的 1 分钟 |
| `OCR_UPSCALE` | 3 | 基准测试 52.6% vs 45% |
| 企业间隔 | 3.5–6.5 s 随机 | 避节奏检测 |
| 单企业重试 | 2 次 | 失败退避 4 s |
| 单批上限 | 50 家 | 超 50 转商业 API |

### 4.3 判定口径

| 判定 | 条件 | 动作 |
| --- | --- | --- |
| `ok` | status ∈ 存续/在业/在营/开业/有效/登记 | 无需动作 |
| `alert` | status 含 吊销/注销/撤销/迁出/停业/清算/歇业/责令关闭 | 提醒主管 |
| `notfound` | 搜索 `total=0` | 提醒主管 + 人工核验 |
| `unknown` | 无精确同名 / 验证码失败 / 响应缺失 | 列候选，人工核对后重查 |

判定优先级写进代码注释（`credit_check.py:99-104`），避免后续维护者改动顺序导致口径漂移。

### 5.2 提醒链路

| 场景 | 退出码 | 行为 |

## 6. 决策记录

| # | 决策 | 备选 | 理由 |
| --- | --- | --- | --- |
| D1 | 用 Camoufox 而非裸 requests | requests + 手工签名 | 瑞数签名需真实浏览器环境，自建成本远高于收益 |
| D2 | 页面内调用 `selfObj.searchAjax()` 而非直连接口 | fetch 直连 | 直连会丢失页面上下文，且更易触发风控 |
| D3 | 精确名称匹配，不模糊兜底 | 取第一条 | 假阳性会让销售误判客户状态，危害大于查不到 |
| D4 | `notfound` 判为"提醒+人工核验"而非"已注销" | 直接判注销 | `total=0` 有多种成因，硬判会误报 |
| D5 | 过码后复用 5 分钟窗口 | 每家单独过码 | 窗口复用把吞吐从 ~30 s/家降到 11 s/家 |
| D6 | 不做离线令牌生成 | 还原令牌算法 | 服务端校验不可伪造（已实证），且维护成本高 |
| D7 | 规模 > 50 家转商业 API | 扩大批量 | 风控风险与合规成本不划算 |

| # | 坑 | 代价 | 如果重来 |
| --- | --- | --- | --- |
| 1 | 默认"点按钮会发请求" | 多轮排查 | 先看事件处理代码，再决定抓包策略 |
| 2 | 把页面"无数据"文案当接口结果 | 一度误判 | 只看响应 JSON |
| 3 | 用 `evaluate_js` 读页面变量判断脚本是否运行 | 差点推翻正确结论 | 用 `search_code` 搜已加载脚本 |
| 4 | 先写模糊匹配兜底 | 上线前才发现假阳性 | 一开始就精确匹配 |
| 5 | 用免费视觉 API 识别验证码 | 遇 429 阻塞 | 先确认验证码字符集（用户纠正为数字字母） |

### 7.3 遗留限制

| # | 限制 | 影响 | 缓解 |
| --- | --- | --- | --- |
| 1 | OCR 单次约五成 | 极端情况单家 20–30 s | 12 次重试 |
| 2 | `notfound` ≠ 一定注销 | 需人工核验 | CSV 备注写明成因 |
| 3 | 只取当前状态 | 无历史轨迹 | 转商业 API |
| 4 | 站点若升级为滑块/点选验证 | 方案失效 | 需重做，无平滑迁移 |
| 5 | 轮询有延迟 | 状态变更不实时 | 转商业 API 的 webhook |

## 8. 可复用方法论

本项目跑完后，沉淀出五条对同类任务通用的做法：

| # | 方法论 | 适用场景 |
| --- | --- | --- |
| 1 | **先判卡点，再选工具**：把"防护很强"拆成具体状态码/响应体，逐层排除 | 任何有反爬的站点 |
| 2 | **源码优先于抓包**：JS 里有完整契约，抓包只能看到一次执行的切片 | 前端逻辑未 VM 化时 |
| 3 | **用已知答案反证**：拿状态已知的样本跑一遍，验证判定口径 | 任何分类/判定逻辑 |
| 4 | **假阳性比漏报更危险**：宁可返回 `unknown` 让人复核，不要猜 | 风控、合规、对外报告类 |
| 5 | **区分客户端状态与服务端校验**：改前端能过不代表能过 | 任何有服务端会话的站点 |

## 10. 一页速览

| 防护类型 | 瑞数（RS）412 挑战 + 强制图形验证码 + 服务端会话校验 |

| 是否绕过技术措施 | **否**。全程真实浏览器正常路径 |

| 规模上限 | ≤ 50 家/批；更大转商业 API |
